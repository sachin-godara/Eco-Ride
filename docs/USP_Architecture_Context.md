## 1. Executive Summary & Problem Context

### 1.1 The Limitations of Conventional Bike-Sharing Systems
Most traditional academic and small-scale bicycle rental systems are designed as passive database record-keeping software. They operate merely as CRUD applications (Create, Read, Update, Delete) where:
1. Users check out a bike, and administrators view a static table of rental records.
2. **Dock Saturation Failures**: Stations in high-demand zones (e.g., student hostels in the morning, academic blocks in the evening) frequently suffer from either complete starvation (0 bikes available) or total dock congestion (0 empty docking slots to return bikes). Conventional software fails silently, allowing riders to arrive at full docks with no return mechanism.
3. **Absence of Rider Incentivization**: Traditional systems treat riding as a pure expense, offering zero feedback on the environmental and personal health benefits generated by choosing non-motorized micro-mobility over fossil-fuel transit.
4. **Poor Concurrency & Thread Blocking**: Existing desktop systems perform calculation loops on the user interface thread, leading to GUI freezes ("Not Responding" state) during active rental metering.

### 1.2 The EcoRide Solution: Dual USP Innovation
To fulfill the explicit mandate of the **NSP Minor Project Guidelines** requiring *"at least one new and unique property/feature (USP – Unique Selling Proposition) that distinguishes the project from existing solutions"*, **EcoRide** introduces two tightly integrated, mathematically grounded innovations supported by a thread-safe architecture:

- **USP #1: Dynamic Dock Rebalancing & Predictive Capacity Routing Engine**
- **USP #2: Eco-Credit Loyalty Engine with Carbon Offset & Health Accounting**

Together, these features elevate the application from a rudimentary desktop rental tool into an intelligent, sustainable, and closed-loop micro-mobility management ecosystem.

## 2. USP #1: Dynamic Dock Rebalancing & Predictive Capacity Engine

### 2.1 The Asymmetric Flow Problem in Campus Micro-Mobility
In campus and urban environments, micro-mobility traffic follows strong directional tidal flows:
- **Morning Peak (08:00 - 09:30)**: High outbound migration from residential hostels toward central academic blocks. Hostel docks become **starved**, while academic docks become **congested**.
- **Evening Peak (17:00 - 18:30)**: Reverse migration from academic blocks and libraries back to hostels and metro connectors.

Without real-time software-guided rebalancing, users arriving at full docks are left stranded, leading to unauthorized dumping, user frustration, and inventory paralysis.

### 2.2 Rebalancing Mathematical Formulation & Threshold Model
EcoRide dynamically evaluates every station's operational health using the **Dock Saturation Ratio ($S_r$)**:

$$S_r = \frac{N_{\text{available}}}{N_{\text{total}}}$$

Where:
- $N_{\text{available}}$ = Current number of bicycles locked at the station.
- $N_{\text{total}}$ = Total physical docking capacity of the station.

The system continuously classifies station status into three distinct mathematical domains:

```
0.00 ────────────────── 0.15 ────────────────────────────── 0.90 ────────────────── 1.00
 [   STARVED ZONE   ]       [     OPTIMAL ZONE     ]        [   CONGESTED ZONE   ]
 (Operator Dispatched)         (Normal Operation)              (Alternative Routing)
```

1. **Starved State ($S_r < 0.15$)**: Available bicycles constitute less than 15% of total capacity. The system flags the station as `STARVED` and pushes an automated rebalance alert to the **Station Operator Dashboard**, prompting the physical transport of bicycles from surplus docks.
2. **Optimal State ($0.15 \le S_r < 0.90$)**: Healthy operating equilibrium allowing both pick-ups and returns without operational bottleneck.
3. **Congested State ($S_r \ge 0.90$)**: Available docks are nearly full ($\ge 90\%$). The system issues early warning notifications to prevent inbound overflow.

### 2.3 Intelligent Return Overflow Prevention Algorithm
When a rider attempts to return a bicycle at a station where $N_{\text{available}} = N_{\text{total}}$ ($S_r = 1.00$):
1. The return transaction is safely intercepted and blocked by the system validation layer.
2. The system executes a geospatial heuristic search across registered stations:

$$\text{Station}_{\text{target}} = \arg\min_{s \in \mathcal{S}_{\text{vacant}}} \Big( \text{Distance}(s_{\text{current}}, s) \Big)$$

3. The UI immediately displays an **Alternative Dock Guidance Dialog**, detailing the nearest station with available empty slots, walking distance in meters, and estimated pedestrian transit time.

### 2.4 Code & Relational Schema Implementation
- **Database Enforcement**: `stations` table enforces `CONSTRAINT chk_dock_capacity CHECK (available_bikes <= total_docks)`.
- **Backend Service**: Handled in `DataRepository.java` and `Station.java`.
- **UI Integration**: Real-time visual capacity meters rendered in `ReturnBikeDialog.java` and operational queue in `AdminDashboard.java`.

## 3. USP #2: Eco-Credit Loyalty Engine & Carbon Offset Accounting

### 3.1 Objective & Behavioral Psychology
Conventional transit platforms offer zero positive reinforcement for sustainable choices. The EcoRide **Eco-Credit Engine** transforms every kilometer pedaled into verifiable ecological savings and immediate economic reward, creating a gamified loop:

$$\text{Riding} \longrightarrow \text{Carbon Avoided} \longrightarrow \text{Credits Earned} \longrightarrow \text{Monetary Fare Discount}$$

### 3.2 Mathematical Modeling of Environmental & Physiological Impact
During every active ride session, the system meters the elapsed duration $t$ (in minutes) and applies verified urban mobility emission constants:

#### A. Estimated Distance Computation ($D$)
Assuming an average urban bicycle transit speed of $14.0\text{ km/h}$:

$$D\text{ (km)} = \left( \frac{t\text{ (minutes)}}{60} \right) \times 14.0\text{ km/h}$$

#### B. Carbon Emissions Avoided ($\text{CO}_2\text{ Offset}$)
Based on Central Pollution Control Board (CPCB) and International Energy Agency (IEA) urban benchmarks, replacing average Indian city car/two-wheeler transit with non-motorized bicycles prevents **$0.21\text{ kg CO}_2\text{ per kilometer}$**:

$$\text{CO}_2\text{ Saved (kg)} = D\text{ (km)} \times 0.21\text{ kg CO}_2/\text{km}$$

#### C. Caloric Energy Expenditure ($E_{\text{kcal}}$)
Calculated based on metabolic equivalent of task (MET) values for moderate bicycling ($7.5\text{ kcal/min}$):

$$E_{\text{kcal}} = t\text{ (minutes)} \times 7.5\text{ kcal/min}$$

#### D. Eco-Credit Reward Generation ($\mathcal{C}_{\text{earned}}$)
For every $0.5\text{ kg}$ of $\text{CO}_2$ emissions prevented, the rider is awarded 1 Eco-Credit:

$$\mathcal{C}_{\text{earned}} = \left\lfloor \frac{\text{CO}_2\text{ Saved (kg)}}{0.5} \right\rfloor$$

### 3.3 Economic Utility: The Dynamic Loyalty Currency
Eco-Credits are not purely vanity badges; they possess direct purchasing power within the platform:
- **Conversion Value**: $1\text{ Eco-Credit} = \text{INR } 1.00$.
- **Redemption Mechanism**: Upon returning a bicycle, the rider can check "Redeem Eco-Credits".
- **Net Fare Calculation**:

$$\text{Net Fare} = \max\Big(0.00, \text{Gross Fare} - (\text{Redeemed Credits} \times 1.00)\Big)$$

- **Transactional Consistency**: The discount is applied, wallet balance debited, and earned credits deposited atomically within a single SQL transaction to guarantee financial integrity.

## 4. Architectural Implementation: EDT-Safe Concurrency & Fail-Safe Persistence

### 4.1 Asynchronous Live Trip Metering (Event Dispatch Thread Safety)
In desktop Java Swing applications, performing time-intensive calculations or tight sleep loops on the main thread freezes the Event Dispatch Thread (EDT), making the window unresponsive.

EcoRide implements an asynchronous `javax.swing.Timer` executing on a dedicated 1000 ms cadence:
- The UI remains completely fluid and draggable.
- Elapsed time, live distance, and dynamic accrued fare update every second.
- If the application window is abruptly closed, the rental status and start timestamp remain persisted in MySQL, ensuring zero data loss upon relaunch.

## 6. Academic Viva Voce Defense Guide (Mid-Term & Final)

### Q1: What is the primary USP of your project, and why did you choose it?
> *"Our project introduces two core USPs: Dynamic Dock Rebalancing and the Eco-Credit Loyalty Engine. We selected dock rebalancing because asymmetrical migration is the #1 operational failure mode of bike-sharing networks—stations near hostels run out of bikes while academic blocks become clogged. Our system solves this algorithmically by calculating saturation thresholds, blocking full returns, suggesting nearest alternative docks, and dispatching rebalance tickets to field staff."*

### Q2: How does the system compute carbon emissions saved? Is it an arbitrary number?
> *"No, it is grounded in published urban transportation benchmarks. We calculate trip distance using the average urban cycling speed of 14 km/h ($D = \text{hours} \times 14$). We then apply the emission factor of 0.21 kg of $\text{CO}_2$ per kilometer, which represents the average greenhouse gas emissions displaced from urban internal combustion vehicles. For every 0.5 kg offset, 1 Eco-Credit is awarded, translating to a ₹1.00 fare discount."*

### Q3: How is dock overflow prevented at the database level?
> *"In MySQL, our `stations` table enforces the integrity constraint `CONSTRAINT chk_dock_capacity CHECK (available_bikes <= total_docks)`. At the application level in `ReturnBikeDialog`, before accepting a bicycle, the system verifies available slots. If `available_bikes == total_docks`, docking is blocked and the system queries the nearest active station with vacant docks, returning its location and distance to the rider."*

### Q4: How do you ensure the live ride timer does not freeze the Java Swing interface?
> *"We isolate background execution from the Event Dispatch Thread (EDT). Instead of using a blocking `Thread.sleep()` loop, we utilize `javax.swing.Timer` which fires periodic tick events asynchronously every 1000 ms. The fare and distance calculations run efficiently and post updates directly to UI components on the EDT without interrupting GUI message queues."*
